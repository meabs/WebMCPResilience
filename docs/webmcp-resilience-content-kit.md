# WebMCP Resilience: launch content kit

This document contains three publishable drafts. They describe the current
implementation, not an aspirational roadmap. External comparisons are current
as of 12 September 2026 and are linked to primary sources.

## 1. Product blog: The test your agent-facing web app is probably missing

**Suggested title:** Your WebMCP tools work. Will your application survive
when they do?

An agent-facing web application has two ways to change the same state: through
the screen and through its exposed tools. That is useful—but it creates a class
of failures that ordinary UI tests and tool smoke tests rarely explore.

Imagine an agent claims the last available booking slot at the same instant a
person presses the button in the browser. Or a tool request is delayed, retried,
cancelled, or duplicated while the application navigates. Each individual
interaction may look valid. The application can still end up in an invalid
state.

**WebMCP Resilience** is an open-source, local resilience-testing framework for
that problem. It opens a real Chromium page with Playwright, discovers the
tools exposed by `document.modelContext`, and runs a scenario that combines UI
actions, tool calls, declared faults, and checks on the application’s observable
state.

The key word is *declared*. The framework does not invent application records,
business data, selectors, or tool arguments. You describe the actors, the
interactions you want to test, the failure modes you want to introduce, and the
invariant that must remain true.

```yaml
name: single-slot-race
actors:
  agent:
    - at: 0ms
      invoke: claim_slot
  human:
    - at: 0ms
      action: click
      selector: '#claim-slot'
invariants:
  - slots.claimed <= 1
```

YAML is intentional: it is the portable, language-neutral scenario contract
that can be reviewed in Git, generated by a coding agent, and run unchanged in
local CLI workflows and CI. Python and pytest integrations consume the same
browser adapter and scenario model; YAML is the handoff format, not a second
test system.

From there, WebMCP Resilience can explore bounded, seeded action schedules;
inject declared latency, timeouts, duplicate calls, cancellation, navigation,
and HTTP faults; and record the result as a portable run bundle. If a scenario
fails, it tries to remove declared actions only when a fresh browser session
still reproduces that failure. The output is an executable minimal reproduction,
not a screenshot and a hunch.

Here is the moment that makes the value concrete:

```text
FAILED  slots.claimed <= 1
observed  slots.claimed: 2
bundle    .webmcp/runs/race-failure/bundle.json
replay    webmcp replay .webmcp/runs/race-failure/bundle.json --json
```

That matters in CI. A saved bundle captures the scenario, browser and canonical
redacted tool inventory, per-tool and complete inventory fingerprints, selected
schedule, observable state, trace, approvals, artifacts, result, and replay
command. `webmcp replay` refuses an incompatible browser capability or live
tool-contract fingerprint instead of silently reinterpreting old evidence.

Baseline comparison classifies added and removed tools, input/output schema
changes, annotation changes, and unchanged tools separately from behavioural
drift. A scenario can optionally pin required inputs, read-only intent, a
declared semantic version, allowed result codes, and deterministic result-count
invariants. This is deliberately bounded: it detects declared structural and
observable contract drift; it does not automatically prove unchanged business
meaning.

The tool remains CLI-first:

```bash
webmcp preflight --ci --json
webmcp validate .webmcp/scenarios/single-slot-race.yaml --json
webmcp run .webmcp/scenarios/single-slot-race.yaml --ci --adversarial --seed 7 --json
webmcp replay .webmcp/runs/<run-id>/bundle.json --json
```

There is also a terminal console and a local MCP control server for coding
agents. Neither creates a second execution path: both delegate to the same
command API used by the CLI. The MCP server has fixed startup policy—project
root, allowed target origins, artifact sensitivity, concurrency, and mutation
authority. A request cannot elevate its own permissions. Read-only agent runs
reject mutating tools and UI actions; sensitive screenshots remain
metadata-only, while textual evidence and traces cross a redaction boundary.

WebMCP Resilience is not a generic MCP inspector, a replacement for Playwright,
or an official conformance suite. It comes after those checks, asking a more
operational question: **when an agent and a human share application state under
bad timing, does the business invariant still hold?**

Chrome’s WebMCP work is proposed and evolving, which makes browser-native
preflight, a narrow adapter boundary, and reproducible evidence especially
important. Chrome’s own tooling is excellent for inspecting live tools and
debugging a call. WebMCP Resilience is for deliberately trying to break the
application around them. [Chrome WebMCP](https://developer.chrome.com/docs/ai/webmcp)

## 2. Technical blog: Building a resilience harness for WebMCP applications

**Suggested title:** From tool discovery to a replayable race condition: how
WebMCP Resilience works

WebMCP Resilience treats an agent-enabled page as a concurrent system. A browser
user, an agent invoking a page tool, and the application itself can each affect
the same state. The framework therefore tests **state invariants under
interleaving**, rather than only whether an individual tool call succeeds.

### Architecture: one execution contract, three surfaces

```text
CLI JSON / terminal console / local MCP agent server
                     │
                CommandAPI
                     │
  scenario validation · browser preflight · runner · reducer · bundle
                     │
     Playwright Chromium + document.modelContext + live application state
```

The command API is the boundary that prevents the console and agent server from
becoming alternative runners. A YAML scenario emitted by the console is the
same file that the CLI validates and executes. An MCP `run_scenario` request is
validated and passed through the same command API. This lets a team operate
entirely through CLI and CI while making agent access a first-class,
machine-readable integration.

### Scenario model

A scenario declares actors, timed actions, faults, state observation, and
invariants. Actors can invoke a discovered WebMCP tool or perform a browser UI
action such as `click`, `fill`, `select`, `navigate`, or `wait`. The runner
resolves declared state references immediately before a call, so a duplicate
fault repeats the same resolved call rather than re-evaluating stale arguments.

Faults are explicit and have explicit timing points. Supported examples include
latency, timeout, duplicate invocation, cancellation, navigation, and HTTP
error injection. With `--adversarial --seed N`, the explorer varies only
declared simultaneous actions and records the selected schedule. It never asks
an LLM to fabricate a flow or application data.

### How the runner observes state

State-based invariants are evaluated against a configured `state_script`: a
JavaScript expression evaluated in the running page which must return an
object, for example:

```yaml
# .webmcp/config.yaml
state_script: window.__resilienceLab.getState()
```

The runner snapshots that object at invariant checkpoints and records the
observation in the trace. If no script is configured, it does not infer state
from DOM text, network traffic, or hidden application internals; it observes
an empty object. This deliberate constraint makes the state boundary explicit.

`scenario.state.tool` is a related but separate mechanism: it invokes a
declared, discovered WebMCP tool and binds its returned data into a scenario's
tool arguments. It is useful for state-aware calls, but is not an implicit DOM
or network scraper.

### Browser-native readiness before execution

`webmcp preflight` is deliberately distinct from MCP protocol conformance. It
loads the real page and records browser/channel, WebMCP availability, native or
compatibility-host mode, secure-context and origin-isolation information,
Permissions Policy, iframe topology, tool schemas and annotations, inventory
changes, and non-executing cancellation/navigation evidence. Findings contain
severity, recommendation, and evidence.

This matters because Chrome documents WebMCP as a proposed standard with
security and policy gates, including origin isolation and the `tools`
Permissions Policy. A cross-origin iframe needs explicit delegation. The
framework makes those facts preflight evidence instead of hidden browser
assumptions. [Chrome’s WebMCP guide](https://developer.chrome.com/docs/ai/webmcp)

### Controlled execution and reduction

The runner starts a fresh browser session for each candidate schedule and
records a unified trace: tool discovery, tool calls/results/errors, UI actions,
state observations, fault injection, cancellation, and invariant outcomes. A
failing scenario can be reduced by removing declared actions, but only after a
fresh browser run proves the failure still occurs. This avoids the common but
misleading shortcut of editing a trace until it looks minimal.

The scheduler operates at declared millisecond offsets in the Playwright and
browser event loops. For actions at the same offset, it starts eligible WebMCP
tool promises in page context before issuing the accompanying UI action, so
the UI can proceed before the tool result is awaited. Playwright commands on a
page are still transport-serialised. This is deterministic at the **logical
schedule** level—not a claim of sub-frame, Chrome DevTools Protocol, or
microtask-level scheduling control. Requested offsets, the selected schedule,
seed, and event timestamps are preserved as evidence.

### Portable, safe evidence

Every command emits `.webmcp/runs/<run-id>/bundle.json`. The versioned bundle
contains the scenario, compatibility requirements, browser capability and tool
inventory fingerprints, canonical redacted contract summary, drift status,
schedule, approval policy, trace, result, and artifact metadata. Recursive
redaction handles sensitive structured fields and URL query credentials,
including common signature and API-key forms. Console and agent reads redact
again at the display boundary, so imported bundles are not trusted merely
because they claim to be redacted. Potentially sensitive screenshots are never
returned through the agent interface and are metadata-only in the console.

Replay validates browser compatibility and live tool inventory before any
scenario action, then reuses the recorded adversarial schedule. A mismatch
returns structured `tool_contract_drift` evidence with safe tool names and
policy impact. The result is a reviewable evidence handoff, not an opaque test
artifact. Structural and observable checks do not claim automatic business
semantic equivalence.

### Agent control without abandoning CLI

The local MCP server speaks newline-delimited MCP JSON-RPC and exposes typed
operations for capability discovery, preflight, scenario validation, template
creation, execution, run listing, replay, bundle summaries, filtered trace
slices, diffs, textual failure/reproduction evidence, and artifact metadata.

Its policy is immutable at startup. It fixes the repository root, permitted
origins, artifact sensitivity, concurrency limit, and whether mutations are
authorised. Navigation targets are resolved before browser execution and then
checked against the allowed origins; ambiguous, scheme-relative, encoded, and
backslash-normalised references are rejected. A read-only policy rejects
mutating UI actions, cancellation, and tools without a read-only hint.

This is defence in depth for agent-originated test requests: immutable origin
and mutation boundaries reduce the chance that an untrusted instruction turns a
test-writing agent into an unsafe browser operator against an internal target.
It is not presented as prompt-injection prevention, a complete SSRF sandbox, or
centralised enterprise governance.

That is a practical integration boundary: agents can inspect, generate,
execute, diagnose, and replay tests without scraping terminal prose, while an
organisation that prefers local CLI-only operation can simply omit the server.

### What it does not claim

WebMCP Resilience does not certify core MCP conformance, prevent prompt
injection, provide cross-browser WebMCP coverage, or replace a browser grid.
Those boundaries keep the framework focused: deterministic behavioural
resilience of a live, agent-enabled web application.

## 3. Marketplace comparison

### Positioning statement

**WebMCP Resilience is the behavioural-resilience layer for WebMCP-enabled web
applications.** It is purpose-built to find, minimise, and replay bugs caused
by concurrent UI/tool activity and declared failures.

| Product or category | Primary job | WebMCP Resilience adds | Recommended relationship |
| --- | --- | --- | --- |
| [Chrome WebMCP / Model Context Tool Inspector](https://developer.chrome.com/docs/devtools/application/webmcp) | Inspect page tools, edit parameters, make manual calls, inspect results/errors, diagnose schemas. | Seeded UI-plus-tool schedules, declared faults, invariants, minimisation, and portable replay evidence. | Use DevTools to develop/debug a tool; use Resilience to test system behaviour. |
| [MCP Inspector v2](https://github.com/modelcontextprotocol/inspector) | Connect to and inspect generic MCP servers through Web, CLI, or TUI clients. | A real browser page, `document.modelContext`, DOM actions, and deterministic stateful resilience testing. | Keep separate; optionally attach Inspector observations to a run as supplementary evidence. |
| [MCP Conformance](https://github.com/modelcontextprotocol/conformance) | Validate core MCP client/server protocol behaviour and produce protocol checks. | Tests whether a live page stays correct when valid calls, retries, UI activity, and failures overlap. | Run both. Do not call `preflight` official MCP/WebMCP conformance. |
| [Microsoft Playwright MCP](https://github.com/microsoft/playwright-mcp) | Give agents structured browser control for exploratory and persistent agent workflows. | A declared, seedable, faultable, reducible, replayable test contract. | Let agents discover flows; save the durable regression as a Resilience scenario. |
| [Playwright Test and Trace Viewer](https://playwright.dev/docs/trace-viewer) | General browser automation, tracing, network/DOM/screenshot investigation. | WebMCP discovery/preflight, UI-tool interleaving, invariants, resilience faults, and compatibility-aware replay bundle. | Foundation and companion, not a replacement. |
| [BrowserStack MCP / Automate](https://www.browserstack.com/docs/browserstack-mcp-server/overview) | Hosted real-browser/device execution, agent-assisted test operations, logs and screenshots. | WebMCP-specific resilience semantics and portable evidence. | Possible execution partner after verifying the exact Chromium/WebMCP capability fingerprint. |

### The category boundary

```text
Chrome DevTools / MCP Inspector / MCP Conformance
      → Is the tool present, well-formed, protocol-correct, and callable?

Playwright / browser clouds
      → Can we automate and execute in this browser environment?

WebMCP Resilience
      → Does the application preserve its business invariants when UI and
        agent-tool operations interleave under failure?
```

WebMCP Resilience does not test whether an AI agent is smart enough to find the
checkout button; it tests whether the checkout application is robust enough to
survive being driven through WebMCP.

### Competitive claims that are safe to make

- “A deterministic resilience-testing and evidence system for WebMCP-enabled
  browser applications.”
- “Combines declared UI interactions and live page-tool calls under controlled
  schedules and declared faults.”
- “Produces reduced, replayable, redacted evidence bundles.”
- “CLI-first, with a terminal console and policy-bound local MCP agent access
  over the same execution contract.”

### Claims to avoid

- “Official WebMCP conformance.”
- “A replacement for MCP Inspector, Playwright, Chrome DevTools, or a browser
  cloud.”
- “Cross-browser WebMCP testing,” until each target browser has verified support.
- “Prompt-injection prevention” or “enterprise policy management.”

### Go-to-market wedge

Start with teams building stateful, agent-actuated workflows: booking,
checkout, approvals, inventory, scheduling, account changes, and operational
controls. The strongest demonstration is short and concrete: a human/UI and
tool race violates one business invariant; the runner finds it; the reducer
creates a minimal reproduction; CI replays the exact bundle.

The adjacent tools are distribution channels, not enemies. Use Chrome DevTools
for tool debugging, MCP Conformance for protocol checks, Playwright for
automation, and vendor grids for scale. WebMCP Resilience owns the test
semantics and evidence contract that connect them.

## 4. Implementation prompts for launch enhancements

These are implementation prompts, not claims that the capability already
exists.

### Prompt: make the state boundary self-explanatory

```text
Add explicit state-observation diagnostics without changing the single
CommandAPI execution path.

- Include `state_observation` in preflight/capabilities and run bundles with
  `mode: state_script | scenario_state_tool | none`, configured source, and
  validation result.
- Keep the existing distinction clear: `state_script` supplies the object used
  to evaluate state invariants; `scenario.state.tool` resolves declared values
  for action arguments.
- When an invariant references absent state, fail before execution with a clear
  remediation message. Do not scrape DOM text or network traffic implicitly.
- Verify a scenario state tool is discovered and carries `readOnlyHint: true`.
- Add unit tests for all modes and an e2e test using
  `window.__resilienceLab.getState()`.
- Update README and this launch kit with exact configuration examples.

Run `.venv/bin/pytest -q` and `.venv/bin/python -m compileall -q src`.
```

### Prompt: expose logical scheduling evidence, not false precision

```text
Extend the portable run bundle with scheduling evidence while preserving replay
compatibility.

- Record requested action offsets, selected logical schedule, adversarial seed,
  and recorded trace timestamps in a versioned `execution.scheduler` object.
- Document that same-offset tool/UI actions use browser-side tool promise start
  before UI dispatch, while Playwright page commands remain transport-serialised.
- Do not claim sub-frame, CDP, or microtask-level determinism.
- Replay must reuse the selected logical schedule, and tests must verify action
  order and schedule descriptor equality rather than wall-clock equality.
- Add JSON schema/contract tests and update the technical blog.

Run `.venv/bin/pytest -q` and `.venv/bin/python -m compileall -q src`.
```

### Prompt: improve the first-run and failure handoff

```text
Add a local `webmcp demo-race` workflow using the included Resilience Forge
fixture. Keep it local; do not introduce a hosted sandbox, npm distribution,
or external deployment in this change.

- Guide or orchestrate demo startup, then execute preflight, validation, a
  seeded adversarial run, reduction, and replay through CommandAPI.
- For failed `run`, `replay`, and `demo-race`, provide a compact human summary
  with invariant, observed state, capability fingerprint, bundle path, reduced
  repro path when present, and exact replay command.
- Keep `--json` a single stable document and add these as structured fields.
- Add CLI contract tests and an e2e test for the vulnerable race fixture.
- Update README and the product-blog terminal example using actual command
  output from a tested run.

Run `.venv/bin/pytest -q` and `.venv/bin/python -m compileall -q src`.
```

### Prompt: publish the agent safety posture precisely

```text
Surface the immutable local-agent policy in capability and run responses.

- Report allowed origins, mutation authority, blocked UI/cancellation actions,
  artifact policy, and navigation-validation policy.
- Preserve pre-execution URL resolution and final-origin validation. Reject
  cross-origin, scheme-relative, encoded, and backslash-normalised targets.
- Preserve read-only denial of mutating UI actions and mutation-capable tools.
- Add focused regression tests for every rejected navigation form and for
  read-only UI/tool denial with no browser side effect.
- Update docs to call this defence in depth for unsafe agent requests, not
  prompt-injection prevention, SSRF containment, or enterprise governance.

Run `.venv/bin/pytest -q` and `.venv/bin/python -m compileall -q src`.
```
